# Security audit — October 2026

- **Scope:** the whole sqldoro extension (`src/core`, `src/drivers`, `src/tunnel`, `src/extension`,
  `src/webview`), its tests, build scripts, packaging and CI workflows.
- **Commit audited:** `main` at the time of writing (post `0.1.1`, PRs #1–#24 merged).
- **Goal:** find anything that could compromise a connected database (unintended writes, destruction,
  exfiltration, guard or read-only bypass, credential theft, tricking the user into damaging data) or
  harm the machine running the extension.
- **Rules followed:** analysis only; no product code was changed. Proof-of-concept scripts were run
  outside the repository against the local Docker test containers only. No real credentials, no
  network targets other than the local containers.

## Executive summary

sqldoro's central safety claim — _a read-only connection cannot write, and dangerous writes are
gated_ — **held up under sustained attack.** No Critical or High issue was found. In particular, **no
way was found to make a read-only connection write, nor to get a write past the production guard
without the user deliberately changing the connection's settings.**

The strongest parts of the design are the two-layer read-only enforcement (a best-effort SQL
classifier _plus_ a server-side read-only session that refuses writes **and** DDL on both engines),
the inline-edit apply path (single-use preview, re-guarded at apply time, optimistic concurrency with
an exactly-one-row check, all-or-nothing transaction), the generated-SQL quoting and parameter
binding, and the webview sandbox (strict nonce CSP, React text rendering, field-by-field message
validation). The MySQL driver also refuses the classic malicious-server `LOAD DATA LOCAL INFILE`
file-read because no infile stream factory is configured.

The findings that do exist are a **Medium** spreadsheet formula-injection in CSV/TSV export and
clipboard copy (the one issue with real impact on the user's machine), plus a handful of **Low** and
**Informational** items: the every-row `UPDATE`/`DELETE` backstop misses column-based tautologies
(`WHERE id IS NOT NULL`), TLS is off by default (including for URL import with no `sslmode`), a
malicious server can grow the extension host's memory through one huge cell, safety-relevant settings
are workspace-overridable, and SSH keyboard-interactive answers every prompt with the password.

## Overall risk assessment

| Area                                         | Verdict                                                                     |
| -------------------------------------------- | --------------------------------------------------------------------------- |
| Read-only enforcement (classifier + session) | **Solid.** Many evasions tried; all blocked. Server blocks writes and DDL.  |
| Production / every-row confirmations         | Solid, except the documented every-row backstop gap (L1).                   |
| Inline editing (preview → apply)             | **Solid.** Re-guarded, optimistic concurrency, exactly-one-row, atomic.     |
| Generated SQL (edits, filters, sort, export) | **Solid.** Identifiers quoted, values bound, server metadata coerced.       |
| Webview / CSP / messages                     | **Solid.** Nonce CSP, text rendering, validated messages, no command URIs.  |
| Credentials & secrets                        | **Solid.** SecretStorage only; logs/history/errors redacted.                |
| TLS & SSH identity                           | Solid verification; weak defaults (L2) and a minor SSH prompt issue (L5).   |
| Malicious server                             | File-read blocked; one memory-exhaustion DoS (L3).                          |
| File import/export                           | Import safe; **CSV/TSV formula injection (M1).**                            |
| Supply chain / packaging / CI                | **Solid.** `ignore-scripts`, allow-list `.vsix`, least-privilege workflows. |

Residual risk is dominated by **M1 (formula injection)**; everything else is either documented
best-effort behaviour or a defence-in-depth improvement.

## Methodology

1. Read the product docs (README, `CLAUDE.md`, `docs/ARCHITECTURE.md`, `docs/RELEASING.md`,
   `SECURITY.md`, `CHANGELOG.md`) and the descriptions of PRs #1–#7, then every source file under
   `src/` plus the relevant tests, build scripts and workflows.
2. For the SQL classifier and guard policy, built adversarial corpora (comments, executable comments,
   nested/unterminated constructs, quoting edge cases, whitespace, CTEs, function calls, multi-statement
   splits, `EXPLAIN ANALYZE`, session-undo statements) and ran them through the real `classifyStatement`
   from the repository under Node.js, flagging any write/DDL/session statement that came back harmless.
3. Reproduced two findings with small PoC scripts against the repository's own functions (CSV export,
   every-row detector).
4. Confirmed the server-side read-only behaviour against the project's own integration test evidence
   and the live MySQL 8.4 and PostgreSQL 18 containers.
5. Inspected the drivers' handling of malicious-server inputs (mysql2 local-infile, metadata coercion,
   regex over server strings), the TLS and SSH verification code, the webview CSP and message parsers,
   the import/export paths, the `.vsix` allow-list and the GitHub Actions workflows.

All PoC code below is inline; nothing was added to the repository except this report.

## Areas covered

The SQL classifier and guard policy; the session-level read-only layer and every execution path; the
automatic `LIMIT` and the server-side sort/filter wrapper; inline editing (generation, concurrency,
TOCTOU, atomicity); the typed confirmations; cancel/kill; the webview ↔ host boundary (CSP, nonce,

### M1 — CSV/TSV export and clipboard copy allow spreadsheet formula injection (Medium, CONFIRMED)

**Files:** `src/core/results/export-format.ts` — `csvField` (lines 64–70) and the `tsvFormatter`
field function (lines 81–85); reached by **Export to CSV/TSV** and **Copy as TSV**
(`src/extension/results/export-file.ts`, `results-actions.ts`).

**Capability:** (b) an attacker who controls a cell value already in the database; (e) the harm lands
on whoever opens the exported file or pastes the clipboard into a spreadsheet.

**Impact on the user's machine:** cell values are written to CSV/TSV verbatim except for RFC-4180
quoting of `" , \r \n` (CSV) or `" \t \r \n` (TSV). A value that begins with `=`, `+`, `-`, `@` (or a
leading tab/CR) is a **formula** in Excel, LibreOffice Calc and Google Sheets. When the victim opens
the export (or pastes a copied cell), the formula runs: it can exfiltrate other cells over
`=HYPERLINK`/`=IMPORTXML`/`WEBSERVICE`, trigger DDE/command execution on older Excel with a click, or
present a malicious link. This is CWE-1236 (formula injection). The database attacker never needs any
privilege beyond writing a string into a row the victim later exports.

**Reproduction (run against the repo's own formatter):**

```js
import { rowFormatter, formatRows, ExportFormat } from 'src/core/results/export-format.ts'
import { MYSQL_DIALECT } from 'src/drivers/mysql/mysql-dialect.ts'

const target = {
  columns: [
    { name: 'note', kind: 'text' },
    { name: 'amount', kind: 'number' },
  ],
  table: ['t'],
  dialect: MYSQL_DIALECT,
}
const rows = [
  ['=1+2', '3'],
  ['@SUM(A1:A9)', '0'],
  ["+cmd|'/c calc'!A1", '0'],
  ['-2+3', '0'],
]
process.stdout.write(formatRows(rows, rowFormatter(ExportFormat.Csv, target)))
// Output (each hostile cell emitted verbatim, i.e. an active formula):
// note,amount
// =1+2,3
// @SUM(A1:A9),0
// +cmd|'/c calc'!A1,0
// -2+3,0
```

**Recommended fix:** before writing a CSV/TSV field (and before putting a cell on the clipboard),
neutralise a leading formula trigger: if the text starts with `=`, `+`, `-`, `@`, tab or CR, prefix a
single apostrophe (`'`) or wrap it as a quoted field with a leading apostrophe, as OWASP recommends.
Keep the NULL-vs-empty distinction. This changes only CSV/TSV/clipboard output, not the data model.

### L1 — Every-row `UPDATE`/`DELETE` guard misses column-based tautologies (Low, CONFIRMED)

**Files:** `src/core/safety/filters.ts` — `isAlwaysTrue` (line 114), `isAlwaysTrueTerm` (line 118),
`isColumn` (line 151), `isSelfComparison` (line 166).

**Capability:** (a) an attacker who authors the SQL the user runs (a shared/imported saved query, a
history entry, pasted text).

**Impact:** the "type the table name" backstop for an `UPDATE`/`DELETE` that reaches every row only
fires when the `WHERE` is absent or a **constant** tautology (`1=1`, `true`, `id = id`). A `WHERE`
that references a column but is still true for every row is **not** flagged, so a mass change runs with
no speed bump. On a writable non-production connection it simply runs; on production the connection-name
confirmation still fires (writes there are gated), and on a read-only connection the write is blocked
entirely — so this weakens a backstop, it does not bypass the primary guarantees.

**Reproduction:**

```js
import { classifyStatement } from 'src/core/safety/classify.ts'
import { POSTGRES_DIALECT } from 'src/drivers/postgres/postgres-dialect.ts'

for (const sql of [
  'DELETE FROM accounts', // FLAGGED
  'DELETE FROM accounts WHERE 1=1', // FLAGGED (constant tautology)
  'DELETE FROM accounts WHERE id IS NOT NULL', // NOT flagged — deletes every row (PK id)
  'UPDATE accounts SET balance=0 WHERE id > -1', // NOT flagged
  "UPDATE accounts SET balance=0 WHERE note LIKE '%'", // NOT flagged
  'DELETE FROM accounts WHERE id IN (SELECT id FROM accounts)', // NOT flagged
]) {
  console.log(classifyStatement(sql, POSTGRES_DIALECT).unfiltered.length > 0, sql)
}
```

**Recommended fix:** this matches the documented best-effort scope (PR #4 chose to gate only constant
`WHERE`s), so the safest change is to the **README wording** — "without a real `WHERE`" overpromises;
say the every-row guard catches a missing or constant-true `WHERE` only. If stronger coverage is
wanted, confirm any `UPDATE`/`DELETE` whose `WHERE` touches only key columns with non-restrictive
operators (`IS NOT NULL`, `>=`/`>` against a type's minimum), while keeping the fail-closed default.

### L2 — TLS off by default, including URL import with no `sslmode` (Low, CONFIRMED)

**Files:** `src/core/connection/connection.ts` — `DEFAULT_SSL` (`mode: SslMode.Disable`, lines 85–91);
`src/core/connection/url.ts` — `parseParameters` folds URL options onto `DEFAULT_SSL` (line 182).

**Capability:** (d) a user importing a connection URL, or creating one in the form.

**Impact:** a new connection, and an imported URL such as `postgresql://app:pw@db.example.com/shop`
with no `sslmode`, resolve to **SSL disabled** — the password and all traffic go in clear text, and no
warning is shown that the connection is unencrypted. `libpq` would use `sslmode=prefer` for the same
URL (opportunistic TLS), so sqldoro is less protective than the tool users may expect. The form does
show the SSL fields before saving, which mitigates the form case; URL import is the sharper edge.

**Recommended fix:** for URL import with no `sslmode`, default to `require` (as the code already does
for `prefer`/`allow`), or add a visible warning that the imported connection is unencrypted; consider
defaulting new non-loopback connections to `require`.

### L3 — A single huge cell from a malicious server can exhaust host memory (Low, PLAUSIBLE)

**Files:** `src/core/engine/query.ts` (`RowCollector`, `maxRows` caps the number of rows but not the
size of a value); the drivers hand whole values to the collector.

**Capability:** (c) a malicious or compromised database server the user connects to.

**Impact:** `sqldoro.results.maxRows` bounds how many rows are kept, and the webview only ever receives
1,000 characters per cell (200,000 in the detail pane), but the **extension host keeps every value
whole**. A server that answers a query with one multi-hundred-megabyte/gigabyte field can grow the
host's memory until it crashes. It is a denial of service (the host restarts), not data loss, and it
needs a hostile server; the 10 MB cell in PR #7 shows large values are otherwise handled. Not
reproduced against a real server to avoid destabilising the environment; the absence of a per-value cap
is clear from the code.

**Recommended fix:** cap the bytes kept per cell at the driver boundary (e.g. a few MB), truncating
with the existing "truncated" flag, independent of the row cap; the detail pane already tells the user
when a value is shown only in part.

### L4 — Safety-relevant settings are workspace-overridable (Low, CONFIRMED)

**Files:** `package.json` `contributes.configuration` — every property uses the default `window` scope;
read in `src/extension/settings.ts`.

**Capability:** (d) a workspace the user has trusted, through `.vscode/settings.json`.

**Impact:** `sqldoro.safety.productionEnvironments` is `window`-scoped, so a workspace can override the
user's value (for example narrow `["prod","staging"]` down to `[]`). `prod` is **always** treated as
production regardless (`productionEnvironments()` always re-adds it), so a `prod` connection stays
protected; but a **custom** production tag such as `staging` could be un-protected by a repository the
user opens. This slightly contradicts the README's "settings can only make the guards stricter".
Workspace Trust gates it (the extension declares no untrusted-workspace capability, so it is disabled
in untrusted workspaces), which keeps the risk low.

**Recommended fix:** give `sqldoro.safety.productionEnvironments` (and arguably the `autoLimit`
settings) `machine` or `application` scope so a workspace cannot weaken them; or re-affirm the user
value when merging.

### L5 — SSH keyboard-interactive answers every server prompt with the password (Low, PLAUSIBLE)

**Files:** `src/tunnel/ssh-connection.ts` — `answerPasswordPrompts` (lines 94–101):
`finish(prompts.map(() => credentials.password))`.

**Capability:** (c) a malicious or compromised SSH jump server.

**Impact:** when the SSH server uses keyboard-interactive auth, sqldoro answers **every** prompt in the
challenge with the configured password, whatever each prompt asks ("Verification code:", "Username:").
A hostile server could phrase prompts to collect the password where it does not belong. The user is
already authenticating to that server with this password, so the marginal exposure is small, but
answering non-password prompts is unnecessary.

**Recommended fix:** answer only echo-off prompts, or only the first prompt, or match the prompt text,
instead of replying to all of them with the password.

### I1 — Privileged server-side file-read functions classify as plain reads (Informational, CONFIRMED)

**Files:** `src/drivers/postgres/postgres-dialect.ts` and `src/drivers/mysql/mysql-dialect.ts`
(`sideEffectFunctions`); `src/core/safety/queries.ts` (`sideEffectCall`).

A `SELECT pg_read_file('/etc/passwd')`, `pg_ls_dir(...)`, `pg_read_binary_file`, `pg_stat_file`, or
MySQL `SELECT LOAD_FILE('/etc/passwd')` classifies as a **read** and is allowed even on a read-only
connection (these are reads; the server's read-only mode does not block them). They read files on the
**database server**, require the corresponding privilege (superuser / `pg_read_server_files` /
`FILE`), and do not modify data, so this is consistent with the documented "classifier is best effort;
database permissions are the guarantee" model. Noted so the owner can decide whether to surface a
warning or add a "server file access" category to the dialects.

### I2 — `SLEEP` / `pg_sleep` / `BENCHMARK` classify as reads (Informational, CONFIRMED)

`SELECT SLEEP(10)` (MySQL) and `SELECT pg_sleep(10)` (PostgreSQL) classify as reads and run on
read-only connections. They tie up a single session and are cancellable, so the impact is a
self-inflicted, recoverable delay — inherent to any SQL client and already noted in the README's known
limits. `isReadOnlyQuery` (used only as a UX/advisory gate, never as the sole security gate) does list
these words, so the server-side sort/EXPLAIN-ANALYZE affordances are not offered for them.

### I3 — MariaDB `/*M! … */` executable comments are not expanded (Informational, PLAUSIBLE)

**Files:** `src/core/sql/scanners.ts` / `src/core/safety/statement-view.ts` recognise `/*!` as an
executable comment but not MariaDB's `/*M! … */`. A MariaDB server runs the code inside `/*M! … */`
while sqldoro's classifier treats it as a plain comment. This is a classifier/server desync, but
MariaDB is explicitly out of the tested scope; on a read-only connection the server session still
blocks any write, so it only affects the every-row/production **backstops** on writable connections of
a MariaDB server. Worth a line in the code or docs if MariaDB support is ever claimed.

### I4 — GitHub Actions pinned to mutable major tags (Informational, CONFIRMED)

`.github/workflows/*.yml` pin `actions/checkout@v7`, `setup-node@v7`, `upload-artifact@v7`,
`download-artifact@v8`, `github-script@v9` by **major tag**, which is mutable. The workflows are
otherwise well-scoped (`permissions: contents: read` by default, no `pull_request_target`, publish
secrets behind a gated `publish` environment), so the exposure is limited to a supply-chain compromise
of a first-party action. Pinning to full commit SHAs (with Dependabot updating them) would close it.

## What held up

These attacks were tried and **failed**; they are the solid parts of the product.

- **Read-only cannot write — the classifier.** A large adversarial corpus for both dialects
  (`/*c*/SET …`, `SET/*c*/ …`, `SET--c\n …`, leading whitespace, `/*! SET SESSION TRANSACTION READ
WRITE */`, `/*!50000 … */`, nested/spaced `set_config(...)`, `"set_config"(...)`,
  `pg_catalog . set_config(...)`, `set_config` inside `CASE`/`WHERE`/`LATERAL`/`VALUES`/subselect,
  data-modifying CTEs, `SELECT … INTO`/`INTO @v`/`INTO OUTFILE`, `FOR UPDATE`, `LOCK IN SHARE MODE`,
  `EXPLAIN ANALYZE <write>`, `COPY … TO/FROM [PROGRAM]`, `PREPARE/EXECUTE`, `DO`, `CALL`, `BEGIN READ
WRITE`, `START TRANSACTION READ WRITE`, `SET TRANSACTION READ WRITE`, `SET SESSION CHARACTERISTICS AS
TRANSACTION READ WRITE`, `SET ROLE`, `SET SESSION AUTHORIZATION`, `USE`, `RESET ALL`, multi-statement
  splits, executable comments carrying a `;`) was run through the real `classifyStatement`. **Every
  write, DDL and session-changing statement came back non-harmless; the only "read" results were
  genuine reads (`TABLE t`, `SELECT SLEEP`).** Fails closed on unterminated strings/comments,
  unbalanced parentheses, unknown first words and `EXPLAIN ANALYZE` it cannot read.
- **Read-only cannot write — the server session.** `SET default_transaction_read_only = on`
  (PostgreSQL) and `SET SESSION TRANSACTION READ ONLY` (MySQL) are applied on every per-database
  connection of a read-only session and re-applied on reconnect. The project's integration tests, and
  the live containers, confirm the server refuses `INSERT/UPDATE/DELETE/REPLACE/MERGE`, data-modifying
  CTEs, `CREATE/DROP/TRUNCATE/ALTER` (DDL too), `nextval`, `FOR UPDATE` and writes in a database the
  session moves to. The statements that could _undo_ the session read-only are all caught by the
  classifier first.
- **Malicious server cannot read client files.** mysql2 3.24.5 refuses a server `LOAD DATA LOCAL
INFILE` request because sqldoro configures no `infileStreamFactory`; it replies with an empty packet
  and reads nothing from disk. PostgreSQL's `pg` + `pg-cursor` path offers no client-side file read.
- **Generated SQL resists hostile identifiers and metadata.** Edit statements quote every identifier
  by doubling the quote character and bind every value as a parameter; the SQL type fragments
  (`parameterType`, `comparedAs`, `collation`) are fixed constants or numbers coerced through
  `Number()`, so a malicious server's column name, collation or precision cannot inject SQL. The
  server-side sort/filter wrapper binds values and quotes unique column names, and is re-classified by
  the guard.
- **Inline editing is safe against surprise writes.** The preview is single-use (`take(previewId)`,
  so a double click or an old preview does nothing); apply re-resolves the current connection and
  re-runs the guard (so a connection that became read-only or production between preview and apply is
  caught — TOCTOU handled); each statement carries the full key plus an optimistic-concurrency check
  and must change exactly one row, so a row changed meanwhile is a conflict and the whole batch rolls
  back.
- **Webview boundary.** Strict CSP (`default-src 'none'`, `script-src 'nonce-…'`, styles/images from
  the extension only, no `unsafe-inline`); `localResourceRoots` limited to `dist/webview`; values
  render as React text (no `dangerouslySetInnerHTML`/`innerHTML` anywhere in product code); every
  webview message is parsed field-by-field and rejected if malformed, row windows are bounded, and the
  webview can never send raw SQL — the host builds every statement from structured messages. Tree
  tooltips are non-trusted `MarkdownString` built with `appendCodeblock`/`appendText`, so a hostile
  table name or SQL string cannot inject a `command:` link.
- **TLS identity.** Both drivers verify the certificate against the **database** host name even through
  an SSH tunnel; `verify-ca` vs `verify-full` map correctly (`checkServerIdentity` skipped only for
  `verify-ca`); mysql2 refuses `verify-full` to an IP through a tunnel rather than checking the wrong
  name.
- **SSH host key TOFU.** SHA256 fingerprints in OpenSSH format, trusted on first use, keyed by
  lowercased `host:port`; a changed key prompts with both fingerprints; a refusal fails the connection.
- **Local tunnel.** The forwarder listens on `127.0.0.1` on an OS-chosen ephemeral port only; a local
  process could reach it but still needs the database credentials (same as `ssh -L`).
- **Secrets.** Only in VS Code `SecretStorage`; never in settings, global state, history, saved
  queries, exports or logs. Logs/errors are redacted of known secrets and URL passwords; history masks
  the strings of password-setting statements (`IDENTIFIED`, any word ending in `PASSWORD`,
  `*secret*`). A grep for secret-bearing log calls found none.
- **Cancel targets only the session's own query.** `KILL QUERY ?` (MySQL, the session's own
  `threadId`) and `pg_cancel_backend($1)` (PostgreSQL, the session's own backend pid), both bound
  parameters, from a second connection — it cannot cancel another session.
- **Imports.** Saved-queries and known-hosts JSON are read through Map-based readers (`Object.entries`
  into a `Map`), so a `__proto__` key cannot pollute a prototype; imported queries get fresh ids and
  de-duplicated names; URL parameters only ever assign a fixed set of SSL keys. No `eval`, `Function`,
  `child_process`, shell, or `openExternal` in product code.
- **Supply chain.** `.npmrc` sets `ignore-scripts=true`; the `.vsix` is an allow-list checked by
  `scripts/package/vsix-rules.ts` (missing/extra file and a size budget); workflows default to
  `contents: read`, use `pull_request` (not `pull_request_target`), and keep publish secrets in a
  gated `publish` environment. The regexes applied to server-controlled strings (the enum-values
  parser, fingerprinting, error-location) use disjoint alternations or simple patterns — no
  catastrophic backtracking found.

## Prioritized remediation plan

Grouped into suggested pull requests, most valuable first.

1. **PR: neutralise spreadsheet formula injection (M1).** In `export-format.ts`, escape a leading
   `=`/`+`/`-`/`@`/tab/CR in CSV and TSV fields (and in the clipboard copy path), keeping the
   NULL-vs-empty distinction; add table-driven tests with hostile cell values for both formats. _High
   value, small, self-contained._
2. **PR: safer connection defaults and clearer every-row docs (L1, L2, L4).** Default URL import with
   no `sslmode` to `require` (or warn that it is unencrypted); scope
   `sqldoro.safety.productionEnvironments` to `machine`/`application`; correct the README's every-row
   wording (and optionally extend the detector to key-only non-restrictive `WHERE`s, fail-closed).
3. **PR: harden against a hostile server (L3, L5, I1, I3).** Cap the bytes kept per cell at the driver
   boundary with the truncated flag; answer only echo-off SSH keyboard-interactive prompts; optionally
   add server-file-read functions to the dialects (or surface a warning) and recognise `/*M! … */` if
   MariaDB is ever supported.
4. **PR: pin GitHub Actions by commit SHA (I4).** Replace major-tag pins with full SHAs and let
   Dependabot update them.

## Appendix — environment and caveats

- PoCs ran under Node.js (type-stripping the repository's TypeScript directly) against the functions in
  `src/`, and against the local `test/integration/compose.yaml` MySQL 8.4 / PostgreSQL 18 / OpenSSH
  containers. No external host was touched; no real credential was used.
- `npm audit` reports **0 vulnerabilities**; it is also a gate on every PR in CI. The runtime
  dependency set is small and current (`mysql2` 3.24.5, `pg` 8.23.1, `pg-cursor` 2.22.1, `ssh2` 1.17.0,
  `react`/`react-dom` 19, `@tanstack/*`), with no publicly known high-severity advisory as of this
  writing.
- This report is analysis only. No product code was changed, and no fix in the plan above has been
  applied.
